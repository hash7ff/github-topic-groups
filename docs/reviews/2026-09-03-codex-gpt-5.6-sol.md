## Findings

### [severity: high] Concurrent edits can erase unrelated topics

- **Where** [service-worker.ts:139](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:139), [service-worker.ts:147](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:147), [github-api.ts:167](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/github-api.ts:167)
- **What** The fresh `GET` and replacement `PUT` are separate operations. If GitHub’s UI, another client, or another extension adds a non-folder topic after the `GET`, this extension’s `PUT` omits and deletes it. The endpoint provides no documented write precondition; GitHub generally does not support conditional unsafe requests unless an endpoint explicitly says so. Thus the absolute “never destroy existing topics” guarantee is not met. [GitHub’s conditional-request guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api), [Replace all repository topics](https://docs.github.com/en/rest/repos/repos#replace-all-repository-topics)
- **Fix** Treat this as a release blocker for the absolute guarantee. Test whether this endpoint actually honors `If-Match`; if it does not, no client-side read/merge/write implementation can guarantee preservation against external writers. Serialize the extension’s own writes and post-verify, but either find an atomic/granular API or explicitly relax and disclose the concurrency guarantee.

### [severity: high] Credential storage is accessible to content scripts

- **Where** [manifest.json:12](/home/mutsuyuki/share/workspace/github-topic-folders/manifest.json:12), [storage.ts:14](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/storage.ts:14), [check-token-isolation.sh:5](/home/mutsuyuki/share/workspace/github-topic-folders/scripts/check-token-isolation.sh:5), [README.md:55](/home/mutsuyuki/share/workspace/github-topic-folders/README.md:55)
- **What** PATs, access tokens, and refresh tokens are stored in `chrome.storage.local`, which Chrome exposes to content scripts by default. The current content bundle does not read them, but the claimed isolation boundary is not enforced; compromised content-script code could read an Administration-write credential. The grep check only proves the current bundle contains no obvious storage references. [Chrome storage documentation](https://developer.chrome.com/docs/extensions/reference/api/storage#property-local)
- **Fix** On installation and worker startup, call `chrome.storage.local.setAccessLevel({accessLevel: "TRUSTED_CONTEXTS"})`. Keep all content access mediated through messages and add a test that executes from a content-script context and confirms local storage is inaccessible.

### [severity: high] Privileged messages trust the content-script context

- **Where** [service-worker.ts:134](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:134), [service-worker.ts:154](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:154), [service-worker.ts:185](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:185), [service-worker.ts:227](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:227)
- **What** `sender.id === chrome.runtime.id` does not distinguish the trusted options page from a less-trusted content script. The worker casts unknown input to `Request` and permits content contexts to invoke `auth.setToken`, `auth.clear`, `journal.list`, arbitrary `prefs.set`, and topic writes for arbitrary owner/repository strings. A compromised content renderer could replace topics on any repository accessible to the token, including repositories outside the supported personal-owner UI. Chrome explicitly advises treating content-script messages as attacker-controlled. [Chrome messaging security guidance](https://developer.chrome.com/docs/extensions/develop/concepts/messaging#security-considerations)
- **Fix** Add runtime schema validation and per-sender capability rules. Restrict authentication and journal operations to `chrome-extension://…/options.html`; restrict repository operations to an exact GitHub repositories-page sender; enforce `owner === resolveLogin()` in every write path; validate batch size, duplicates, repository membership, and operation shape.

### [severity: high] Writes are not bound to the state and configuration the user confirmed

- **Where** [messages.ts:41](/home/mutsuyuki/share/workspace/github-topic-folders/src/core/messages.ts:41), [content.ts:175](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:175), [content.ts:198](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:198), [service-worker.ts:135](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:135), [topicsMerge.ts:11](/home/mutsuyuki/share/workspace/github-topic-folders/src/core/topicsMerge.ts:11)
- **What** A bulk item contains only owner, repository, and target project—no expected old topic, prefix, dry-run value, or configuration revision. Rename/delete membership comes from a cache up to five minutes old, while the worker rereads preferences for every item. If a repository moves from A to B elsewhere before “Delete A,” the fresh `GET` sees B and the helper removes B. Changing the prefix during a bulk can make later items remove a different prefix, and changing dry-run can produce a mixed real/dry operation that is reported as “nothing written.” The New Project picker also includes conflicted repositories, allowing the generic setter to remove all their existing folder topics without using Fix.
- **Fix** Send an immutable operation envelope containing the prefix, dry-run snapshot, configuration revision, and expected current folder topic(s). After the fresh `GET`, abort that repository if the expectation differs or a new conflict exists. Snapshot settings once per bulk and exclude conflicts from generic creation/move flows.

### [severity: high] In-flight refresh can undo sign-out or replace newer authentication

- **Where** [token-manager.ts:17](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/token-manager.ts:17), [token-manager.ts:27](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/token-manager.ts:27), [service-worker.ts:193](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:193)
- **What** Refresh persists its result without checking whether authentication changed while the request was in flight. A successful refresh can restore credentials after the user clicked Sign out or overwrite a newly saved PAT; a failed refresh unconditionally calls `clearAuth()` and can erase newer credentials. Temporary network/5xx failures also permanently remove an otherwise valid refresh token.
- **Fix** Serialize all authentication mutations through the token manager and attach a persisted generation/version to the auth record. Commit or clear a refresh result only if the current generation still matches. Retain credentials on network, rate-limit, and 5xx errors; clear only for definitive invalid/expired-refresh responses.

### [severity: high] Store-facing privacy disclosures contradict the implementation

- **Where** [privacy.html:32](/home/mutsuyuki/share/workspace/github-topic-folders/site/privacy.html:32), [privacy.html:33](/home/mutsuyuki/share/workspace/github-topic-folders/site/privacy.html:33), [privacy.html:36](/home/mutsuyuki/share/workspace/github-topic-folders/site/privacy.html:36), [privacy.html:39](/home/mutsuyuki/share/workspace/github-topic-folders/site/privacy.html:39), [storage.ts:95](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/storage.ts:95), [github-api.ts:153](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/github-api.ts:153)

Its preservation promise is hard-coded to `topic-folders-` despite a configurable prefix. It also lacks the affirmative Limited Use declaration currently required for products handling sensitive user data. Chrome Web Store policy requires an accurate, comprehensive, current privacy policy, so this should block submission. - **Fix** Correct the implementation first, then update the policy, homepage, README, in-product disclosure, and Store dashboard to enumerate every stored/transmitted field, retention period, endpoint, recipient, configurable-prefix behavior, and Limited Use compliance.

### [severity: medium] Mutation scheduling is per operation and ignores rate-limit backoff

- **Where** [service-worker.ts:152](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:152), [service-worker.ts:168](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:168), [service-worker.ts:227](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:227), [github-api.ts:81](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/github-api.ts:81)
- **What** Each Port serializes only its own items. Two GitHub tabs, two ports, or a direct write during a bulk can issue concurrent PUTs without global one-second spacing. Concurrent journal/cache read-modify-writes can also lose entries. When GitHub supplies `Retry-After`, the loop still continues after one second, potentially making every remaining item fail or prolonging the restriction. [GitHub REST best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- **Fix** Route every mutative request through one worker-side scheduler that enforces global serialization and spacing. Persist a `retryUntil`, honor `Retry-After` and `x-ratelimit-reset`, and pause or defer remaining bulk items.

### [severity: medium] A confirmed no-op can leave the UI showing stale ownership

- **Where** [service-worker.ts:142](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:142), [storage.ts:107](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/storage.ts:107), [content.ts:229](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:229)
- **What** When the fresh topics already match the requested target, `setProject` returns `unchanged` without updating the cached repository. The content script then reloads with `force=false`. For example, if the cache shows A but GitHub was externally changed to B, choosing B reports “Nothing to change” while continuing to display A for up to five minutes.
- **Fix** Patch the cache from the fresh `current` topics even on unchanged results, and perform one forced repository-list refresh after each completed single/bulk operation. Add cache generation checks so an older list request cannot overwrite a newer patch.

### [severity: medium] Write failures leave GitHub’s native list hidden

- **Where** [content.ts:229](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:229), [content.ts:232](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:232), [content.ts:270](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:270)
- **What** After a single or partial bulk failure, the code reloads into `phase.kind === "ready"` and displays only an error flash. `applyMode()` therefore keeps the native list hidden. The Original switch remains usable, but this still violates the stated rule that GitHub’s list is never hidden during an error state. A Port rejection similarly leaves the prior ready phase active.
- **Fix** Represent write/operation failures as an explicit error-bearing phase that forces `anchor.hidden = false`, or automatically switch to Original while retaining the partial-results panel.

### [severity: medium] Async view instances survive Turbo replacement

- **Where** [content.ts:100](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:100), [content.ts:304](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:304), [content.ts:317](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:317), [dialog.ts:27](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/ui/dialog.ts:27)
- **What** Disposal depends on finding the old root in the current document. If Turbo removes that root before `mount()` runs, `existing` is null and the old instance is never marked disposed. Its pending loads or writes continue, and dialogs appended directly to `body` can survive profile-frame navigation. A newly mounted view has an independent `busy` flag, permitting overlapping operations. Repeated Refresh clicks also have no request-generation guard, so an older response can render last.
- **Fix** Keep one module-level active view independent of DOM lookup, dispose it on every route generation, own and close its dialogs, and use generation IDs or abort signals for loads. Coordinate write-busy state through the worker rather than per view.

### [severity: medium] Bulk progress is not durable across MV3 worker termination

- **Where** [service-worker.ts:165](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:165), [service-worker.ts:168](/home/mutsuyuki/share/workspace/github-topic-folders/src/background/service-worker.ts:168), [bulk.ts:18](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/bulk.ts:18)
- **What** Remaining items, successes, and failures exist only in local arrays. A 300-repository operation already spends roughly five minutes in explicit delays before network time. Port messages help the idle timer, but Chrome still documents termination risks and limits for long requests/fetches. If termination occurs, the UI receives only a generic disconnect and cannot identify completed, failed, or unprocessed repositories. This is a platform-risk finding; it was not reproduced in this review. [Chrome service-worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle#idle-shutdown)
- **Fix** Persist an operation record and per-item outcome before/after every step, return an operation ID, support status/reconnect/resume, and process work in bounded chunks below lifecycle limits.

### [severity: low] The MutationObserver watches every DOM mutation on every GitHub page

- **Where** [manifest.json:23](/home/mutsuyuki/share/workspace/github-topic-folders/manifest.json:23), [content.ts:333](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:333), [content.ts:348](/home/mutsuyuki/share/workspace/github-topic-folders/src/content/content.ts:348)
- **What** The content script observes the entire `document.body` subtree even outside profile repository pages, instead of the targeted profile Turbo frame described in the implementation plan. Mutation-heavy pages continually reset the debounce and add unnecessary work; sustained mutations can postpone a needed mount.
- **Fix** Restrict injection with an `include_globs` where practical, attach the observer only on matching repository routes, and observe `turbo-frame#user-profile-frame` or rely primarily on Turbo navigation events.
